# Plan: Browser pane as a Ghostty split pane (mirror of the text-editor pane)

## Goal

Add a simple, clean web-browser pane to Niftty that lives in the split tree exactly like the text-editor pane does — full tiling/drag/zoom/zen support for free — with a start tab themed by the Niftty config (`background` + `background-opacity`).

## Current context / assumptions

- The repo is a Ghostty fork ("Niftty"). macOS app in `macos/`, built **only** via `zig build` from the repo root (artifact `zig-out/Niftty.app`). Never call `xcodebuild`/`swift build` directly for app builds (see `.agents/skills/building-the-app/SKILL.md`).
- The exact precedent to copy is the **text editor pane** (commit `aa8782808 "editor"`, improved in `a805c194e`). It works like this:
  - `macos/Sources/Features/Editor/EditorPane.swift` defines `EditorDocument` (ObservableObject), `EditorPaneStore` (an `NSMapTable<Ghostty.SurfaceView, EditorDocument>` singleton with weak keys), a `SurfaceView.editorDocument` accessor, a focus notification, and the SwiftUI `EditorPane` view.
  - The pane's `Ghostty.SurfaceView` is a real terminal surface whose command is `/usr/bin/true` with `waitAfterCommand = true` (process exits instantly; the surface stays alive so the split tree, focus, drag handle, zoom, and zen mode all keep working).
  - The real terminal view is embedded **hidden at opacity 0** (`Ghostty.InspectableSurface(...).opacity(0).allowsHitTesting(false)`) for focus/drag plumbing, plus a `Ghostty.SurfaceGrabHandle` overlay for drag-rearrange.
  - `TerminalSplitLeaf` (`macos/Sources/Features/Splits/TerminalSplitTreeView.swift:100`) swaps in `EditorPane` when `surfaceView.editorDocument != nil`.
  - `BaseTerminalController.newEditorSplit(at:direction:document:)` creates the split; `moveFocus(to:)`, `split(direction:)`, `close(_:)`, and `focusedSurfaceDidChange(to:)` special-case editor panes.
  - `AppDelegate.openEditor(_:)` + a File-menu item in `macos/Sources/App/MainMenu.xib` (⌘O) are the entry point.
  - `Ghostty.SurfaceView` is `Codable`; `editorPath` is an optional `CodingKey` in `SurfaceView_AppKit.swift:1963-2014` and restore re-attaches the document. Additive optional keys do **not** need a `TerminalRestorableState` version bump (the migration test pins version 7 / minimum 5 — leave both unchanged).
- The Xcode project uses `fileSystemSynchronizedGroups`, so **new Swift files are picked up automatically** — no pbxproj edits (the editor commit touched none).
- App is **not sandboxed** (see `macos/Ghostty.entitlements`), so WKWebView has normal network access. `import WebKit` is a system framework; no new dependencies.
- Deployment target is macOS 13.1. CI builds with an **older pinned Xcode** — use only long-stable APIs (no `@Observable`, no Swift 5.9+ shorthand beyond what the editor file already uses).
- User-taste constraints from the request: simple, clean interface; the empty/default tab must use `ghostty.config.backgroundColor.opacity(ghostty.config.backgroundOpacity)` exactly like `EditorPane` does (`macos/Sources/Features/Editor/EditorPane.swift:106,116`).

**AGENTS.md feature-integration evaluation (state these in the final report, they are deliberate):**
- *Keybinding*: exposed as a File-menu item with shortcut ⇧⌘B, exactly like the editor pane's ⌘O menu entry. A `Binding.zig` action (`new_browser_pane`) is deliberately **not** added: it would require touching `src/input/Binding.zig`, `src/apprt/action.zig`, `src/apprt/embedded.zig`, `include/ghostty.h`, and both apprts, and the editor-pane precedent handles pane-type creation at the AppKit menu layer. Revisit if the user wants a config-file keybind.
- *Settings UI*: nothing new is configurable — the pane deliberately reuses the existing `background` / `background-opacity` config, so no new Settings entry. No new config keys (YAGNI).

## Architecture / proposed approach

Mirror the editor pane end-to-end: a `BrowserDocument` + `BrowserPaneStore` attached to a real `Ghostty.SurfaceView` (backed by `/usr/bin/true`), rendered by a SwiftUI `BrowserPane` that swaps into `TerminalSplitLeaf`. Web content is a `WKWebView` wrapped in `NSViewRepresentable`, shown only once a URL exists; the empty state is a pure-SwiftUI start page painted with the theme background at the configured opacity. Address-bar input is normalized by a pure, unit-tested function (`BrowserDestination.destination(for:)`). Everything else (tiling, resize, equalize, drag-rearrange, zoom, zen, window restore) is inherited from the split-tree plumbing the editor already uses.

import AppKit

/// Normalizes address-bar input into a navigation destination.
///
/// - Explicit http/https/file URLs are kept as-is.
/// - Host-like input (has a dot, is localhost, or is an absolute path) gets an
///   https:// prefix.
/// - Everything else becomes a DuckDuckGo search.
/// - Unknown schemes and empty input are rejected (return nil, no dispatch).
enum BrowserDestination {
    static func destination(for input: String) -> URL? {
        let trimmed = input.trimmingCharacters(in: .whitespacesAndNewlines)
        guard !trimmed.isEmpty else { return nil }

        if let url = URL(string: trimmed), let scheme = url.scheme?.lowercased() {
            if ["http", "https", "file"].contains(scheme) {
                return url
            }
            return nil
        }

        let hostLike = trimmed.hasPrefix("localhost")
            || trimmed.hasPrefix("/")
            || (trimmed.contains(".") && !trimmed.contains(" "))
        if hostLike, let url = URL(string: "https://\(trimmed)") {
            return url
        }

        var components = URLComponents()
        components.scheme = "https"
        components.host = "duckduckgo.com"
        components.queryItems = [URLQueryItem(name: "q", value: trimmed)]
        return components.url
    }
}

/// The state of one browser pane. Owned by `BrowserPaneStore`, keyed weakly
/// by its hosting `Ghostty.SurfaceView` — same lifecycle as `EditorDocument`.
final class BrowserDocument: NSObject, ObservableObject {
    /// The current page URL, or nil when the pane shows the start page.
    @Published var url: URL?
    @Published var addressText: String = ""
    @Published var pageTitle: String = ""
    @Published var isLoading: Bool = false
    @Published var canGoBack: Bool = false
    @Published var canGoForward: Bool = false

    init(url: URL? = nil) {
        self.url = url
        self.addressText = url?.absoluteString ?? ""
    }

    /// Navigate from address-bar input. Nil destination (unknown scheme or
    /// empty) is a no-op.
    func navigate(_ input: String) {
        guard let target = BrowserDestination.destination(for: input) else { return }
        addressText = target.absoluteString
        url = target
    }
}

final class BrowserPaneStore {
    static let shared = BrowserPaneStore()

    private let documents = NSMapTable<Ghostty.SurfaceView, BrowserDocument>(
        keyOptions: .weakMemory,
        valueOptions: .strongMemory
    )

    private init() {}

    func document(for surface: Ghostty.SurfaceView) -> BrowserDocument? {
        documents.object(forKey: surface)
    }

    func attach(_ document: BrowserDocument, to surface: Ghostty.SurfaceView) {
        documents.setObject(document, forKey: surface)
    }
}

extension Ghostty.SurfaceView {
    var browserDocument: BrowserDocument? {
        BrowserPaneStore.shared.document(for: self)
    }
}

extension Notification.Name {
    static let browserPaneFocusRequested = Notification.Name("com.niftty.browserPaneFocusRequested")

private struct BrowserWebView: NSViewRepresentable {
    @EnvironmentObject private var ghostty: Ghostty.App
    @ObservedObject var document: BrowserDocument
    let box: WebViewBox

    func makeCoordinator() -> Coordinator {
        Coordinator(document: document)
    }

    func makeNSView(context: Context) -> WKWebView {
        let webView = WKWebView(frame: .zero, configuration: WKWebViewConfiguration())
        // Pages draw their own background; behind content, use the theme so
        // there is no white flash during loads.
        webView.underPageBackgroundColor = NSColor(ghostty.config.backgroundColor)
        webView.navigationDelegate = context.coordinator
        box.webView = webView
        context.coordinator.observe(webView)
        if let url = document.url {
            webView.load(URLRequest(url: url))
        }
        return webView
    }

    func updateNSView(_ webView: WKWebView, context: Context) {
        // Load only when the model points somewhere the webview isn't yet.
        // In-page navigation updates the model from didCommit, so this never
        // double-loads.
        if let url = document.url, webView.url != url {
            webView.load(URLRequest(url: url))
        }
    }

    final class Coordinator: NSObject, WKNavigationDelegate {
        private let document: BrowserDocument
        private var cancellables: Set<AnyCancellable> = []

        init(document: BrowserDocument) {
            self.document = document
        }

        func observe(_ webView: WKWebView) {
            webView.publisher(for: \.canGoBack)
                .assign(to: \.canGoBack, on: document)
                .store(in: &cancellables)
            webView.publisher(for: \.canGoForward)
                .assign(to: \.canGoForward, on: document)
                .store(in: &cancellables)
            webView.publisher(for: \.title)
                .map { $0 ?? "" }
                .assign(to: \.pageTitle, on: document)
                .store(in: &cancellables)
            webView.publisher(for: \.estimatedProgress)
                .map { $0 < 1.0 }
                .removeDuplicates()
                .assign(to: \.isLoading, on: document)
                .store(in: &cancellables)
        }

        func webView(_ webView: WKWebView, didCommit navigation: WKNavigation!) {
            document.url = webView.url
            document.addressText = webView.url?.absoluteString ?? ""
        }
    }
}

## Risks, tradeoffs, and open questions

- **First-load flash**: WKWebView paints its own background once a page loads; only the start tab is themed. Mitigated by `underPageBackgroundColor` = theme background. Full page-transparency is not possible with public API (the `drawsBackground` KVO trick is private API — deliberately avoided).
- **Focused-value gap**: while the WKWebView itself is first responder, `@FocusedValue(\.ghosttySurfaceView)` is unset (it's set on the address field), so a few focus-value-driven behaviors may not see the surface. The hidden `InspectableSurface` + controller-level `focusedSurface` keep split/focus/drag working; same class of caveat as the editor pane when its gutter is focused.
- **CI toolchain skew**: only long-stable APIs used; if `NSColor(SwiftUI.Color)` or any KVO-publisher line fails on the pinned Xcode, fall back per the inline note in Task 3.
- **Undo/redo of "Open Browser"** works through the existing `insertSplit` undo plumbing; redo re-creates an **empty** browser pane (document state isn't in the undo stack). Same tradeoff the editor makes on redo (it re-opens the file).
- **Deliberately out of scope (v1)**: history/bookmarks persistence, multiple tabs inside one pane, Cmd+L address-bar focus shortcut, per-pane context menu, downloads UI, error pages (failed loads show a blank page + retained URL). Defaults chosen: DuckDuckGo for non-URL input; pane opens as a right-split of the focused surface; ⇧⌘B shortcut. All trivially changeable later.
- **GTK app**: untouched — this is macOS-app-layer only, like the editor pane.
